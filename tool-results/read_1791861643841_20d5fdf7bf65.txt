    20→Single source of truth: `src/lib/order-status.ts` — transition map + Persian labels + allowed-actor check.     22→`DRAFT` is **client-only** (the existing builder draft in localStorage/Zustand).     24→| State | Meaning (fa) | Allowed transitions → | Actor | SMS on entry |
    25→|---|---|---|---|---|
    26→| `DRAFT` | سبد/ساخت هدیه (client-only, not in DB) | `AWAITING_PAYMENT` (checkout POST) | customer | — |

    41→## 2. Checkout API — server-authoritative
    42→
    43→One endpoint creates the order; nothing about money is trusted from the client. Today the total is computed in **4 places** (`flow.tsx` ×2, `pay-modal.tsx`, `store.placeOrder`) and POSTed as-is; shipping is displayed but never charged. All of that dies.
    44→
    45→**`POST /api/checkout`** (auth: session cookie if logged in, else guest; rate-limit §5):
    46→
    47→```jsonc
    48→{
    49→  "idempotencyKey": "uuid-v4 (generated once, persisted in localStorage pendingOrder)",
    50→  "items": [{ "variantId": "bear-lg", "qty": 1 }],        // 12 SKUs; qty small int
    51→  "addons": { "charmHearts": 0, "charmPaws": 2 },          // prices from Setting
    52→  "sender":   { "name": "...", "phone": "09xxxxxxxxx" },   // guest checkout = identity anchor
    53→  "recipient": { "name", "phone", "province", "city", "address", "postalCode" },
    54→  "occasion": "birthday|valentine|yalda|...",
    55→  "cardMessage": "...", "anonymous": false,
    56→  "paymentMethod": "zarinpal" | "manual"
    57→}
    58→```
    59→
    60→Server-side decisions, each with rationale:
    61→
    62→1. **Server-authoritative pricing.** Server loads `ProductVariant.priceToman` + box/charm prices from `Setting`, computes `shippingFee` from `Setting` (`ship_fee_tehran` / `ship_fee_other`, province-based; **never free** — answer `free_thr: never`), returns `total`. Client MUST render the returned total and pay exactly it. — *Rationale:* kills the ×4 client-total and the fake client-side coupon in one move. — *Rejected:* sending prices from client and "verifying" them (race-prone, still trusts client); *rejected:* coupon engine now (answer: later — but the totals response already carries `discount: 0` so a coupon row slots in later without contract change).
    63→2. **Idempotency.** `Order.idempotencyKey @unique`. Same key retried → returns the **same** order (`200`, not a second row). Client keeps `pendingOrder = { key, code, total }` in localStorage and retries the same key on reconnect; the success screen **blocks on server ACK** (polls `GET /api/checkout/{key}/status` until it returns the order state, max ~2 min, then falls back to SMS confirmation). — *Rationale:* critic's decision — a key alone is inert; it pays off only with client retry + ACK-blocking success. — *Rejected:* separate IdempotencyKey/replay-cache table (a unique column gives the same guarantee with one table); *rejected:* Redis-based idempotency middleware (no Redis).
    64→3. **Server order code.** `PN-YYMMDD-####` (e.g. `PN-260214-0007`), `####` from an `OrderSeq` counter row incremented inside the same transaction; `code @unique` makes the retry path safe. Human-readable, dictatable over the phone, fits SMS. — *Rejected:* keeping client-generated `no` (13-a proved the `@unique` race silently drops orders at concurrency); *rejected:* cuid/UUID as customer-facing code (unspeakable in Persian phone support).
    65→4. **Atomic stock decrement (oversell-proof on SQLite).** Inside `prisma.$transaction`: `db.productVariant.updateMany({ where: { id, stock: { gte: qty } }, data: { stock: { decrement: qty } } })`; if `count === 0` → abort → `409 { error: "sold_out" }`. A single conditional `UPDATE … WHERE stock >= qty` is atomic under SQLite's single-writer WAL — no reservation table needed. Release on `CANCELLED`/`EXPIRED` (increment back). — *Rejected:* Reservation/Hold table with TTL sweeps (12 SKUs don't justify it); *rejected:* `SELECT`-then-`UPDATE` (classic oversell race).
    66→5. **Guest checkout fields & validation.** Sender mobile `09xxxxxxxxx` (Persian digits normalized via one shared `normPhone` module — today it's duplicated ×3) is the identity anchor; postal code 10 digits; province from a fixed 31-province list; address ≤ 400 chars; `anonymous` hides sender name from the gift. No password, ever. — *Rationale:* matches answer `guest: yes` + Kavenegar contactability.
    67→6. **Voice note & printed card.** Card message is a checkout field; the voice note is uploaded **after** order creation to `POST /api/orders/{code}/voice` (multipart, ≤ 2 MB, `audio/webm|mp4|m4a` mime-sniffed) — keeps checkout JSON-only and lets slow uploads fail without losing the order.
    68→7. **What replaces `bootSync()`:** see §4 — checkout responds with `{ order: { code, status, total }, payment: {...} }` and nothing else needs the global dump.
    69→
    70→**Success/ACK contract:** Zarinpal redirect-back lands on the success screen with `?code=`; screen polls `GET /api/checkout/{key}/status` (authorized by key possession; returns only `{code, status, total}` — no PII) until `PAID | PAYMENT_UNDER_REVIEW | FAILED`. Manual flow lands on a "transfer instructions + upload receipt" screen (§3).

   108→## 5. OTP Hardening + In-Process Rate Limiting (NO Redis)
   109→
   110→**`src/lib/rate-limit.ts`** — in-process token buckets keyed `scope:id`, `Map` with lazy expiry; returns `429` + `Retry-After`. Config table (one place):
   111→
   112→| Scope | Limit | Why |
   113→|---|---|---|
   114→| `otp_request:phone` | 3/hour **+ 60 s cooldown between requests** | SMS cost burn + harassment |
   115→| `otp_request:ip` | 10/day | distributed abuse |
   116→| `otp_verify:phone` | 5 per code / 15 min | brute force (4-digit code = 10k space) |
   117→| `checkout:ip` | 5/10 min | checkout spam / stock pinning |
   118→| `review:phone|ip` | 2/hour | UGC spam (13-a: reviews publish instantly) |
   119→| `receipt:order` | 6/hour | upload abuse |
   120→| `contact:ip` | 3/hour | form spam |

   123→
   124→**Restart behavior (documented, accepted):** buckets live in process memory → a deploy/restart resets limits. Worst case is one extra burst per deploy on a single instance — acceptable; the SMS-burn scopes are additionally bounded by the DB-side counters above.    153→## 7. Background Jobs — systemd timers → signed internal endpoints
   154→
   155→**No in-process cron** (`node-cron`/`setInterval` dies with deploys and double-runs under dev hot-reload). One `POST /api/jobs/{name}` route family, each guarded by constant-time compare of the `x-cron-secret` header against env `CRON_SECRET`; timers live in systemd on the VPS (`OnCalendar`), each just `curl -sS -X POST -H "x-cron-secret: …" http://127.0.0.1:3000/api/jobs/{name}`. Every run appends a row to `JobRun { name, startedAt, finishedAt, ok, detail }` — cheap audit the AI can read when debugging. All jobs are **idempotent** (safe to double-fire).
   156→
   157→| Timer | Job | Action |
   158→|---|---|---|
   159→| every 10 min | `expire-unpaid` | `AWAITING_PAYMENT` (and `FAILED`) older than **24h** → `EXPIRED`, **stock released** |
   160→| every 2 min | `sms-flush` | send queued `SmsOutbox` rows, backoff ×3 (§6) |
   161→| hourly | `abandon-cart` | `AWAITING_PAYMENT` age > **6h** and `smsAbandonedAt IS NULL` → enqueue `abandon_cart` **once** (set flag) — no extra table needed |
   162→| hourly | `low-stock` | variants with `stock ≤ Setting.low_stock_threshold` → enqueue `low_stock` to admin (once per crossing) |
   163→| daily 04:30 | `backup` | **pre-hook pattern**: `sqlite3 db.custom "…/.backup …"` + tar `/data/uploads` → `/data/backups/`, prune > 14 days |
   164→| daily 05:00 | `purge` | stale `AuthCode`, expired `Session`, old `JobRun` |
   165→
   166→— *Rationale:* single-instance boring infra, survives deploys, visible in `systemctl list-timers`. — *Rejected:* in-process scheduler (dies with the app); *rejected:* a separate worker service + queue (constraint: one app, one VPS); *rejected:* GitHub Actions cron (data residency must stay in Iran).
